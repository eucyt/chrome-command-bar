# ワーカーへの依頼文

`CLAUDE.md` は毎回読まれるので繰り返さない。並行だからこそ必要なのは次の 2 つ。

1. **他の sub-issue との関係を具体的に書く。** 「この関数は #m が作るのでそれを使う」「この値は #k と同じ数え方に揃える」。重複した実装は後で衝突として跳ね返る
2. **範囲を閉じる。** 完了条件と「要件」の範囲を超えない。超えそうなら止まって報告する

## 型

```
次の issue を 1 本実装してください。進め方と検証は CLAUDE.md に従います。

issue: #<番号> <タイトル>(<URL>)
親 issue: #<番号>(設計はここ。読んでから始める)
ベースブランチ: main
ブランチ名: feat/<番号>-<短い英語の説明>

依存: <なし / #m はマージ済み>
他の issue との関係:
- <#m が同じ <対象> を触る。<揃えること / 使い回すこと>>
- <既にある <仕組み> を使い、二重に作らない>

守ること:
- 完了条件と「要件」の範囲を超えない。超えそうなら止まって報告する
- CLAUDE.md や親 issue の設計と矛盾する実装が要るなら、実装せず issue にコメントして止まる
- `npm run check` を通してから PR を作る。PR 本文には `Closes #<番号>` を入れる
- 画面を変えたなら、実機テストのスクリーンショットを自分で確認する
- rebase と force push をしない。main の取り込みはマージコミットで行う
- マージは指揮側(またはユーザー)が行う。PR を作ったあとは、CI が赤になったとき以外 push しない
- PR を作ったら、PR の URL・head の SHA(40 文字)・検証結果・他の issue に影響しそうな点を短く報告する
```

## 衝突を返すとき

依頼文ではなく、同じセッションへの追加メッセージで返す。添えるもの:

- 衝突するファイルと、衝突の塊の位置
- こちらで `git merge` を試したときの出力(失敗したテスト名、エラーの箇所)
- 原因の見立て(「#m が関数の引数を変えた。古い呼び方が残っている」など)
- どちらの行を残すか。両側が別のものを足しただけなら「両方残す」と書く
- 相手側の PR の URL
