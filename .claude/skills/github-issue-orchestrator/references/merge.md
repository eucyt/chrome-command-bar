# マージの判断と、並行で踏む落とし穴

## マージの判断

1. **CI がすべて success であることを見る。** 一部が pending のまま入れない
2. **入れる前に、必ず手元で実際に `git merge` を走らせて確かめる。** 両側が触ったファイルの数を数えて衝突と読まない。触ったファイルが同じでも、衝突しないことは多い

   ```sh
   git fetch origin
   git checkout -B verify origin/main
   git merge --no-ff origin/<ブランチ>   # 2 本目以降はここに重ねていく
   npm run check
   ```

3. **2 本以上をまとめて入れるときは、main に 1 本ずつ重ねて、そのつど `npm run check` を通す。** 大きい変更を先頭に置く。後ろに置くと重ねるたびに落ちて、その完了を待つ下流が止まる
4. 画面を変える PR は、実機テストのスクリーンショットを指揮側も開いて確かめる
5. ユーザーがマージすると決まっているなら、1〜4 の結果と入れる順を添えて報告し、マージしない
6. 指揮側が入れるなら、スカッシュでマージしてブランチを消す

   ```sh
   gh api -X PUT repos/OWNER/REPO/pulls/<番号>/merge -f merge_method=squash -f sha=<head の SHA 40 文字>
   gh api -X DELETE repos/OWNER/REPO/git/refs/heads/<ブランチ>
   ```

   `sha` を付けると、確かめたあとに push された PR を誤って入れずに済む。ワーカーは短縮 SHA で報告してくることがあるので、PR の `head.sha` で引き直す。

衝突しない main の取り込みは、ワーカーに「指揮側が取り込むので push しない」と伝えてから行う。

```sh
gh api -X PUT repos/OWNER/REPO/pulls/<番号>/update-branch
```

**衝突するときは取り込まない。** 解消はワーカーに返す(`worker-brief.md` の「衝突を返すとき」)。

## 単体の検査では見つからない壊れ方

並行実装でいちばん多い失敗。どちらの PR も自分の検査は緑なのに、重ねると壊れる。PR の検査は自分のブランチしか見ていないので、原理的に見つからない。

- 片方が関数の名前や引数を変え、もう片方が古い呼び方のまま書いている
- テストの補助関数が両方のファイルに同じ名前で入り、重複で落ちる
- 片方が設定や定義データの形を変え、もう片方が古い形で新しい項目を足している

いずれも衝突として現れない。触った行が違えば `git merge` は黙って通す。だから 1 本ずつ重ねて検査を通す。

## 衝突を直すときの落とし穴(ワーカーに返す材料)

- **衝突の塊の外に共有の末尾がある。** 片側が関数やテストの途中で切れていて、閉じ括弧が塊の外にある。機械的に両側をつなげると構文が壊れる
- 定義の一覧(コマンド、許可リスト、テストの手順)の衝突は、ほとんどが「両側が別のものを足しただけ」。どちらかを選ぶ話ではなく、両方残せば済む
- 中断したマージが置いた未追跡ファイルが残ると、次に試すブランチを巻き添えにする。`git merge --abort` と `git clean -fd` で落としてから次へ進む
- ブランチが依存を足していると、手元の `node_modules` に無くて落ちる。PR のせいではないので、`npm ci` を入れ直してから検査し直す

## 履歴の扱い

`rebase` と `force push` をしない。取り込みはマージコミットで行う。指揮する側とワーカーが同時に直したとき、履歴を書き換えると相手の作業が消える。同時に直してしまって push が弾かれたら、そこで手を引いて相手に任せる。

## CI の挙動

- 同時に多数が push すると、検査の実行が作られるまで数分遅れることがある。慌てない
- 「flake」は原因ではない。再実行は、テスト本体が走る前に死んだ(checkout、install、ランナーの消失)ときか、同じコミットで一度通っているときに限り 1 回だけ。2 回目の失敗は本物として扱う
- 実機テストが落ちたら、CI のアーティファクトにあるスクリーンショットを見る
