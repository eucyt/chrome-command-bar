# 並列実装の指揮

複数のセッションが同時に issue を実装し、PR を次々に main へ入れる進め方を、GitHub の親 issue と sub-issue だけを台帳にして回す。

指揮する側の仕事は次に限る。親 issue に設計を書く、sub-issue に分割する、ワーカーを起動する、状態を確認する、マージ可否を判断する、ワーカーに連絡する、終わったセッションを片付ける。
**指揮する側はコードを書かない。ブランチに push しない。衝突の解消も自分でやらない。**
自分で直し始めると、そのブランチを持つワーカーと同じ場所を同時に触ることになり、どちらの作業も失われる。
例外は 2 つ。**衝突しない main の取り込み**(GitHub の Update branch)は、ワーカーに伝えてから行ってよい。**手元で衝突を解消して検証する**のは、ワーカーに返す材料を作るためならよい。解消した結果は push せず、「どちらの行を残すか」を渡す。

## 参照ファイル

| ファイル | 読むタイミング |
|---|---|
| `references/issues.md` | 最初。親 issue と sub-issue の書き方、分け方、GitHub API の呼び方 |
| `references/worker-brief.md` | フェーズ 3。ワーカーに渡す依頼文の型 |
| `references/merge.md` | フェーズ 5。マージ判断の手順と、並行で踏む落とし穴 |

## ユーザーへの連絡

ユーザーは並列実装を放置して別の仕事をしていて、通知を見た時点で文脈を忘れている。

- 1 行目に `🔴【要判断】` か `🟢【報告・返答不要】` を置く
- 何の件か・いまの状態・止まっている理由を毎回書き直す。「先ほどの件」で済ませない
- 1 問 1 論点で短く聞く。聞くのは、答えで進め方が変わり、後から直すと高くつくものだけ
- 質問・承認・可否の確認は、選択式の質問ツール(AskUserQuestion)で出す。推奨を先頭の選択肢にして `(推奨)` を付ける。本文に質問を書いて返信を待たない
- 報告は 4 行程度。管理記録の表やセッションの内部情報は貼らない

## 入口の判定

渡されたものを GitHub で読み、どれかを見分ける。

- **sub-issue の無い issue**(目的・要件・完了条件が書かれている)→ フェーズ 0 から。これを親 issue にする
- **sub-issue のある親 issue** → フェーズ 0 のあと、フェーズ 3 の起動から
- **issue 番号の列挙** → 共通の親 issue があればそれを辿る。無ければ、束ねる親 issue を作るかをユーザーに聞く
- **issue がまだ無い依頼** → 依頼の内容で親 issue を作ってからフェーズ 0

目的や完了条件が書かれていない issue は、そのまま進めず、何が足りないかをユーザーに伝えて止まる。土台が無いまま分割すると、sub-issue どうしの境界が曖昧になり、後で衝突として跳ね返る。

## フェーズ 0: 準備

1. `CLAUDE.md` と親 issue を読む。`CLAUDE.md` の「守ること」に反する設計は書かない。反しないと実現できないなら、実装せずユーザーに止める
2. 決まっていること、決まっていないこと、読み方が複数ある点を分けて整理する。後の 2 つは、**設計や分割を書き始める前に、1 回にまとめてユーザーに聞く**。推測で埋めた設計は、並列に走り始めてから誤りが分かり、複数の PR をまとめて作り直すことになる
3. **マージを誰がするかを同じ質問で確認する。** 指揮側が入れてよいか、ユーザーが自分で入れるか。答えはその親 issue の間ずっと守る
4. 人の判断が要る場面を先に伝える。「不明点の確認」「分割結果の承認」「(ユーザーがマージする場合)マージ」の 3 つで、それ以外は自動で進めると明言する

## フェーズ 1: 親 issue に設計を書く

- 親 issue の本文に**設計**を足す。何を作るか、モジュールと責務の境界、データと契約、やらないこと。型は `references/issues.md`
- **sub-issue ごとに考慮が要る細かいこと(触るファイル、テストの書き方)は書かない。** 親と子の両方に書くと、片方だけ直って食い違う
- 元の本文(目的・要件・完了条件)は消さずに残し、その下に設計を足す

## フェーズ 2: sub-issue に分割する

- **1 sub-issue = 1 ブランチ = 1 PR。** 大きさと分け方は `references/issues.md`
- sub-issue には**具体的で網羅的な実装内容を端的に**書く。ワーカーはこの本文と `CLAUDE.md` だけを頼りに実装する
- 依存は sub-issue の「備考」に `依存: #n` と書き、親 issue の分割表にも載せる。**依存の無い sub-issue を増やす**のが並行の効き目を決める
- 親 issue の本文に「分割」の表(順・issue・依存・状態)を書く

**分割ができたら止まって承認をもらう。** sub-issue の一覧・依存・並行できる本数を表 1 つで示し、可否は AskUserQuestion で聞く。承認が出るまでワーカーを起動しない。分割の質がその後の衝突の数を決める。

## フェーズ 3: ワーカーを起動する

**着手できる sub-issue**は、依存先がすべて main にマージ済みのもの。依存先が未マージの間は起動しない。

- **sub-issue ごとに 1 セッション**で、作業ツリーを分ける。別セッションを起動する道具があればそれを使い、無ければ worktree を分けたサブエージェントを使う。同じ作業ツリーを 2 つのワーカーに触らせない
- 依頼文は `references/worker-brief.md` の型で書く
- モデルや effort はユーザーの指定に従う。指定が無ければ既定のままにし、難易度を理由に勝手に変えない
- 起動したら、親 issue の分割表の状態を「実装中」にする

## フェーズ 4: 定期確認と管理記録

5 分間隔で、実行中の sub-issue を一括・簡潔に確認する。sub-issue ごとに次の 1 行だけを管理記録としてチャット内に持つ。

```
issue | タイトル | 依存 | セッション | PR | CI | 最終状態
```

状態に変化がない間は、履歴や差分を読み直さず、通知もしない。次の変化があったときだけ記録を更新して処理する。

- 依存先のマージ、sub-issue の開始・完了
- PR の作成・更新、CI の成功・失敗
- 衝突、繰り返す検証失敗、入力待ち

親 issue の分割表は、状態が変わったときだけ書き換える。毎回書き換えると履歴が荒れ、人が見たときに何が変わったのか分からなくなる。

障害の扱い:

- **衝突・統合の失敗** → そのブランチを持つワーカーに返す。こちらで試して分かったこと(衝突するファイル、失敗したテスト、原因の見立て)を添える
- **PR をまたぐ修正が要る** → 既存のワーカーに足さず、新しい sub-issue を立てて専任のセッションを作る
- **ワーカーが `CLAUDE.md` や設計との矛盾で止まった** → 親 issue の設計を見直すか、ユーザーに判断を仰ぐ。「とりあえず進めて」と言わない
- **入力待ち** → 判断できるものは答え、できないものはユーザーに 1 回で聞く。複数のワーカーが同時に止まったら 1 通に束ねる

## フェーズ 5: マージ

判断の手順は `references/merge.md`。要点は次のとおり。

- CI がすべて success であることを見る。そのうえで**必ず手元で実際に `git merge` を走らせて確かめる**
- 2 本以上をまとめて入れるときは、main に 1 本ずつ重ねて、そのつど `npm run check` を通す。片方ずつ緑でも重ねると壊れる
- フェーズ 0 でユーザーがマージすると決めたなら、指揮側はマージしない。入れられる状態になった時点で、PR の URL・検証結果・入れる順を報告する
- 指揮側が入れる場合はスカッシュでマージし、ブランチを消す
- PR 本文の `Closes #n` で sub-issue は自動で閉じる。指揮側は閉じない。閉じていなければ PR 本文を確かめる
- マージのたびに、**依存していた sub-issue が着手可能になるので、フェーズ 3 に戻って起動する**
- `rebase` と `force push` をしない。ワーカーにも依頼文で念押しする

## 終了

- すべての sub-issue が閉じたら、親 issue の分割表を最終状態にして親 issue を閉じる(親は自動では閉じない)。ユーザーがマージする PR が残っているなら閉じずに報告する
- ユーザーに完了を報告する。入れた PR、人に委ねた PR、途中で外した・足した sub-issue、次に人がやることを書く
- 終わったセッションと worktree を片付ける。動いているセッションを残すと次の確認でノイズになる
